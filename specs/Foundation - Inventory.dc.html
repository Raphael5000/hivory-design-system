DS vs portal

Built in the product, absent from the system.

The board above measures the components that HAVE a page. This measures the opposite direction: things the console and proposal genuinely render, whose rules live inside a product file instead of in the design system. Each one works — the debt is that rebuilding it means reverse-engineering one file.

Tracked changesFully built \u2014 a real word-level diff (trackHtml() + artTracked in the console\u2019s logic), deletions struck red at 55%, insertions on a green wash, \u201cYour change\u201d with Keep / Undo, and editing back to the original clears tracking. The most complex behaviour in the product and the least documented: it exists as prose in the doctrine and as code in one file, nowhere in between.
Pill fieldFully built in the invite flow (invPills, invKeyDown): emails commit to removable pills on comma, Enter or space, Backspace on empty pops the last, pasted commas split. Real input behaviour with no spec.
Ask popoverBuilt (artNoteFor / artNoteText) and load-bearing: every change verb routes through it rather than firing blind. The doctrine specs its copy in detail; the system has no page for it.
Drop zoneBuilt in the Knowledge upload flow (\u201cDrop files here\u201d, Browse files, \u201cOriginals are stored unchanged\u201d). Distinct from Image slot \u2014 that takes a picture into a draft, this takes a FILE into Knowledge.
Card dismissThe doctrine calls it \u201cone primitive, everywhere\u201d \u2014 a hover-revealed 20px white \u2715 chip straddling a card\u2019s top-right corner. Used across Performance. No page.
Not yet verifiedDate range presets, the attachment chip and the scorecard spine were flagged by a coverage probe that matched page names by first word and produced at least two false positives \u2014 Chart Kit already covers scorecard/spine and chart/spark. Re-audit by reading before building; a bad list is worse than no list.
