Design System
Component · Checkbox & switch

Agreement, and settings.

Two controls that look similar and mean different things. A checkbox is a value you are about to commit; a switch is a setting that has already taken effect. Choosing the wrong one lies about when the change happens.

Both are live \u2014 click, or Tab to them and press Space. The checkbox waits for a form; the switch would already have saved.
Variants

Two, and the rule for choosing.

16px at --radius-sm. For a value that saves with a form or a decision \u2014 an authorisation, a selection in a filter, a task in a list. Nothing happens until something else is pressed.
30\u00d718 with a 14px knob. For a setting that takes effect the moment it moves \u2014 notification preferences, a source going two-way. There is no Save button anywhere near it.

The checked fill is --ink-950, never green. Green is the system's single signal colour \u2014 spending it on agreement would make every consent row compete with a live indicator.
Content rules

What the label may say.

A positive statement the user is agreeing to, sentence case, no trailing period: \u201cI'm authorized to sign for Pure Good\u201d. Never a negative \u2014 \u201cDo not email me\u201d makes a checked box a double negative that nobody parses correctly. Never a question. For a switch the label names the state when ON, not the action: \u201cEmail me when work is held\u201d, not \u201cToggle email\u201d. The label is always clickable and always adjacent \u2014 a 16px target alone fails the 44px rule, and the label is what makes the row big enough to hit.
Do
Put the ring on the box, so it shows what Space will toggle. Grey the label with the control so the pair still reads as one object. Let a saving switch stay interactive and report the save on the row.
Don't
A green checked state. A spinner inside a switch \u2014 it hides whether the value took. A switch beside a Save button. A ring around the whole label. A checkbox that acts immediately, or a switch that waits for a form.
