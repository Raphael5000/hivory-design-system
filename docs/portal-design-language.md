## Principles
1. **One surface level.** Cards sit directly on the canvas. Never a card inside a card. Panels never wrap panels.
2. **One glass object per screen: the sidebar.** Everything else is solid.
3. **Elevation = priority.** Exactly one elevated card per screen (the thing needing the user). Everything else: hairline ring + 1px shadow.
4. **Green is a signal, never decoration.** Live dots, deltas, brand mark, agent activity. Never text on white below green-700. Never a count badge.
5. **Counts are quiet.** Tabular gray text or neutral gray pill — never colored.
6. **The system is dense so the product isn't.** 13px working type; air lives at the edges (page padding), not between rows.

## Rhythm — the vertical ladder (codified 31 Jul; governs every surface)
Space is how a screen says what belongs together. The 4px grid governs the INSIDE of controls (padding, heights, insets, icon boxes); it is the wrong instrument for rhythm, because at section scale it offers twenty indistinguishable options and the eye reads RATIOS, not increments. Audit that forced this: 22 distinct gap values in use — every integer from 1 to 20 — and 1,146 off-ladder margins across 39 files. Spec + live specimen: `Foundation · Rhythm.dc.html`.
SEVEN RUNGS, each ≈1.6× the last, each with exactly one job. An eighth value is always a decision someone avoided making.
- **3 · Bond** — a value and the label that names it. The tightest legal gap. (absorbs 1 · 2 · 4 · 5)
- **8 · Pair** — a glyph and its text, a title and its subtitle, two lines that read as one thought. (absorbs 6 · 7 · 9 · 10)
- **12 · Sibling** — one row from the next; a heading from the paragraph it belongs to. (absorbs 11 · 13 · 14)
- **20 · Block** — one self-contained block from the next inside a section; the default grid gap between cards. (absorbs 16 · 18 · 22 · 24)
- **34 · Group** — a run of blocks from the next run; the widest gap that still reads as one section. (absorbs 26 · 28 · 30 · 32)
- **64 · Section** — one section from the next. Sits above a heading, never below it. (absorbs 48 · 52 · 56 · 60)
- **104 · Chapter** — one page-level region from the next, where a spec page changes subject. FOUND, not designed: every component page was already using 84–100 and no rung could say it. (absorbs 84 · 88 · 96 · 100)
Laws:
- **Eyebrow, heading, lede are one unit** — all 12 apart REGARDLESS of the heading's size (27px or 66px), then 34 to the first block. Scaling that gap with the type is what makes big headings float.
- **Section gaps are asymmetric** — a heading belongs to what follows it: 64 above, 12 below. Equal space orphans it between two blocks.
- **Gaps grow going up the tree** — never let a child gap equal or exceed its parent gap; that is the most common rhythm bug.
- **Space is the only grouping device** — before reaching for a rule, card, wash or border, spend a rung. Most boxes in a first draft are a spacing problem wearing a container.
- **Never nudge by 1–2px** to fix an optical problem — the cause is almost always a wrong rung one level up. Sub-perceptual distinctions are entropy, not craft.
- **Mocks are exempt** — anything imitating another surface keeps the measurements of the thing it depicts (a 44px avatar, a 38px record row). The ladder governs Hivory's own chrome and stops at the mock's edge.
- **Print has its own ladder** — documents are set in points against a fixed page; the px rungs do not convert.
- **Display sizes** (the platform scale stops at 21 because the console has no hero moments): 27 card/section heading · 36 page heading · 48 proposal section opener · 66 hero. Tracking tightens as size grows (−0.03 → −0.045em).

## Markdown Kit (core component family — .md files are a platform primitive)
Every source, document, and the memory itself renders as a .md through exactly these components (spec: Kit · Markdown.dc.html v2 — judged on WHOLE FILES: it leads with two composed specimens, a live document and a mid-generation draft, then the vocabulary):
- `md/file-header` — title 23/680 + ONE descriptor line 12px #8A8D90 (mono filename folded into the descriptor) · hairline. Never a third heading level.
- `md/headings` — H1 23/680 (file title, once) · H2 14/650 (+28px) · H3 13/600 (+20px) · H4 10.5/650 caps (rare); never deeper
- `md/p` 13.5/1.7 #3A3C3E, measure 620px
- `md/list` — plain bullets: INK dash (green dash is facts-only); nest 20px, two levels max · `md/ol` mono gray numerals · `md/task` — checkbox 13px r4; done = struck faint
- `md/link` green-700, underline on hover only · `md/emphasis` bold 600 ink, no italics · `md/divider` hairline, 22px margins
- `md/figure` — extracted images: radius 10, caption 11.5 #9DA0A3 with page ref
- `md/fact` — green-600 dash + statement + provenance in parentheses (always)
- `md/updated` — old value struck #9DA0A3 → new bold + UPDATES MEMORY pill (green-50 wash)
- `md/question` — amber wash block + answer pills; the only amber element; ambiguity never guesses
- `md/quote` — 2px green-500 left rule, #55585B text, attribution with page
- `md/entry` — memory append row: green "+" + statement + source; append-only, newest first
- `md/edit` — hover "fix" → the line becomes editable in place: a green caret, no box, no ring; an edit writes a memory entry
- `md/table` — 10.5 uppercase header, hairline rows, mono numerals right · `md/code` — system-face chip on ink-50, tabular-nums
- `md/draft-bar` — counts + Add to memory / Discard; only on drafts
- `md/colophon` — one lifecycle line + quiet actions (repair → neutral → destructive), verbs never wrap; ends every live file
- `md/records` — DB-backed sources only, and OUTSIDE the document: a plain WHITE CARD of its own (same surface as the file pane), 12px below it, spacious (28/56 padding). Title "Stored in the database" 15/650, no subline. Then group rows (14px apart, 20px below the title): group label 12/600 #8A8D90 in a 110px column ("Deals", "Contacts"), fields as the house chip (Channel-chip form, no glyph): 22px pill, radius 999, ink-5% wash, 11.5/600 #55585B, capitalized plain words ("Close date", never close_date), wrapping with 6px gap. NO dots, NO tracked caps, NO corner annotations, NO mono, no counts, no verbs. Console chrome, not file content: never prints, exports or enters memory.
Kit law: a file is **live** (read & fix) or a **draft** (updated/question/draft-bar active; nothing applies until approved). No third state.
Journey law (Connect & Upload, see Paper · Knowledge journeys.dc.html): nothing enters memory without being shown; ambiguity becomes a question; every fix is a learning; read-only consent by default.

## Records vs Knowledge (codified 28 Jul — the db-vs-md doctrine)
Three layers, one rule each. The .md renders what the engine LEARNED, never what the source STORES.
1. RECORDS — rows in the source system or the engine's warehouse (sessions, orders, deals, posts). Never rendered as a data browser, never edited in the console (read-only consent; HubSpot stays the system of record). Records are QUERIED — by the Analyst via Performance widgets and chat reporting — never browsed. The only client verb on records is ASK.
2. KNOWLEDGE — the graph: what the engine believes. Extracted facts, rules, joins, corrections; append-only, provenance on every line. The only layer the client reads and fixes.
3. THE .MD — layer 2 filtered to one source, rendered by the Markdown Kit. Writable as markdown because facts are prose — never a dump of layer 1.
Frontend: DB-backed sources surface layer 1 through `md/records` (see kit list) — a fields card of its own, below the file pane. Wrong number in a widget → fix the FACT in Knowledge or Reauthorize the source; guard against the Meaning mistake in file form (a data browser inside Knowledge).

## Confirmation rule
Any double confirmation is a modal — never inline UI, never a browser dialog: 380px white panel, radius 16, on a 28% ink scrim (click scrim = cancel). Title = verb + object + "?" (15/650). One-sentence consequence in plain language (12.5 #55585B). Footer right-aligned: Cancel (outline pill) + the verb (red #B91C1C fill for destructive, ink fill otherwise). 140ms fade.

## Responsiveness (rules now, build at screens-locked milestone)
Desktop-first; the phone experience is the DECISION moment, not the whole console.
- Breakpoints: ≥1100 full · 720–1100 compact · <720 mobile.
- Compact: rail collapses to icon rail (56px, labels on hover); content measures already fluid.
- Mobile: rail becomes a bottom bar (Home · Requests · Schedule · Knowledge · more); Knowledge two-pane becomes list → file with back; review sheet goes full-screen; all 2-col grids stack; decision bars pin to the bottom edge (thumb reach); hit targets ≥44px.

## Request chat — states & rules (dev contract)
- Anatomy: user = ink-5.5% wash bubble (radius 16/16/5/16, right-aligned, max 78%); engine = plain text on canvas — the 16px hex mark hangs in a LEFT GUTTER outside the content column, so engine text, steps, artifact cards and the composer card all share ONE aligned left edge; artifacts = white cards (icon tile, title, status sub, ›) that open the side panel; composer pinned bottom (white pill card, attach + Send), its card edge on the same column edge.
- Sessions are agent-locked: a session has a TITLE and an OWNING AGENT, fixed at creation by routing — but the client never sees ops chrome: the chat header is ‹ back + title ONLY (no held/running counts, no agent name). The agent surfaces only inside the steps disclosure ("Session: <Agent>"). The first step of every reply reads "Session: <Agent>". No agent-swapping inside a session.\n- Out-of-scope asks: the agent declines in one sentence ("That's outside this session — it's locked to the <Agent>") and offers a "Start a new session" chip that carries the ask (prefilled on Home) so routing happens fresh. Never silently re-route mid-session.
- Thinking: while working, show ONE line max — the dual-hex spinner (the brand mark’s two shapes counter-rotating in 60° gear-click steps, 1.15s, house easing; seamless via 6-fold symmetry) + plain-language present-tense label ("Thinking — reading memory…"). Never stream reasoning paragraphs; never stack thinking lines. The label may morph as phases change.
- Tool calls/steps: collapsed by default behind "› N steps · duration" (11px faint); the › chevron rotates 90° (soft motion) when open — no glyph swapping. Expanding shows one line per step: green check + client-language description ("Checked HubSpot & Analytics", never API names). Steps never interleave with prose.
- Resolution: the thinking line is REPLACED by the reply (with its steps disclosure) — thinking text never persists.
- Artifact panel geometry (reconciled 29 Jul): panel width clamp(320px, 42vw, 460px), floating 12px off the top/right/bottom edges; the chat column yields margin-right = panel width + 28px (one formula, 16px visual gutter) and drops to 24/8 padding. Below 1100px the panel OVERLAYS chat instead of squeezing — chat never compresses under its 320px floor. Thread-header meta (summary link, agent name) fades out while the panel is open. Decision bar in panel footer; Expand ⤢ grows the panel in place; Esc: expanded → panel → chat.

## Notifications — where "job done" lives (decided 29 Jul)
The console never buzzes. Three surfaces, by tense:
- **While you're in it** — completions and approvals confirm as a quiet TOAST (DS Toast grammar: ink #17181A chip, bottom-right stack, radius 12, green-500 tone dot, 12px line, green "View ›" action → the Work queue, ✕ dismiss, ~7s auto-dismiss, one soft rise-in). Fired on: plan approved · post/article approved (with schedule) · sequence approved · deploy completed ("Deployed — <url> is live").
- **When you arrive** — Home carries one arrival line under the greeting (green dot · "Since <day> — N jobs finished, N held for your review" · "Work queue ›"): the while-you-were-away digest, one line, never a feed.
- **Away from the console** — the email digest and held-work notices (account-menu toggles). 
The Work queue stays the ledger of record; every notification points there. No bell, no tray, no unread badges beyond the rail's existing count pill.

## Artifact Kit — the slide-out contract (one frame, seven bodies)
Every artifact — in the chat panel AND the full sheet — uses the SAME frame: header (title 12.5/650 · Expand ⤢ · ✕), scrollable body, footer decision bar (owner label left; verbs right). Only the body varies, and it is always exactly one of seven renderers:
1. `art/post` — social content as the platform's own card (avatar, handle line, text, media). Verbs: Request changes · Approve & release.
2. `art/article` — blog/newsletter as a reading page: title 20/680, byline/meta 11.5 gray, hero figure (md/figure), prose via the Markdown Kit at 620 measure. Verbs: Request changes · Approve & publish. The article body is a BLOCK EDITOR (Bear/Notion), never a static preview. Blocks: paragraph · heading (14.5/650) · quote (2px green-500 rule) · image (16:9 placeholder, caption editable). Journeys: (1) every block, the title, and the post text are DIRECTLY EDITABLE in place (contentEditable) — no editor chrome, no Save/Cancel row, no textarea swap: click and type (green caret, no box); clicking away commits the wording verbatim as a TRACKED CHANGE (Google-Docs suggestion grammar): a word-level diff renders in place — deletions struck through (red, 55% opacity), insertions on a green-50 wash — with a "Your change" attribution row + Keep / Undo ghosts under the block (Keep accepts and clears the marks; Undo restores the original; editing back to the original clears tracking automatically); Enter commits (single-block grammar), Esc cancels the edit; the title edits verbatim without tracking; memory logs "You, draft edit"; committing empty restores the original — blocks are never deleted directly; removals are requested in words via the change verb. Edit inputs prefill via a whole-value ref that sets el.value once on mount (camelCase DOM attributes like defaultValue are lowercased and dropped by the template runtime — never use them). (2) hover a block → a single quiet "+" ghost at the right — it opens an inline ADD row of paper chips (Text · Heading · Quote · Image) inserting below; new text blocks focus straight into typing. No per-block comment or delete ghosts: feedback travels through the ask popover on the change verb, removals are asked for in words, and the client's own wording changes are tracked edits. (3) comment = a 2px amber-rule note under the block — no label, no wash box; the rule is the label. Input is borderless with quiet Add/Cancel ghosts; saved notes show remove only on hover. Notes collect, the meta line counts them, and the change verb becomes "Send N notes to the Writer". Word count and draft number recompute live from blocks. Expand/collapse is an icon-only ⤢/⤡ ghost in the panel header (tooltip carries the word) toggling full-width document mode in place (680 measure, 27px title, 14px body) — never a modal; expanded, the panel fills the MAIN area only (left edge at 244px), the rail always stays visible.
3. `art/page` — website work has NO visual preview and NO code: SUMMARY OF CHANGES (plain-language facts, marker column) → a quiet change tally under a hairline (mono +a green-700 · −b red · "lines changed · N files" gray). Code never shows — the client approves outcomes, not diffs; file paths and environment names stay out of the panel meta. Verbs: Request changes (ghost text — the secondary action never competes for footer width) · Commit to staging (outline) · Commit & publish (ink). The decision-bar row wraps as a safety net; verbs never cross the footer padding. Committing swaps the body for the BUILD state — the deploy theater: the dual-hex mark gear-clicking (1.15s house motion) above a phase-morphing label (Building → Deploying to <env> → Verifying) + mono elapsed timer, over a three-node PHASE RAIL (Build · Deploy · Verify): done = green check node, active = green node with white core + radiating nodePulse, upcoming = hollow ring; connectors tint green as phases pass. → on completion the ARRIVAL: a 46px hex-check pops in (artPop overshoot) with one radiating ring, "Live on staging / in production" 15/650, "Built and verified in <t>" quiet, and the URL as a white mono pill with a live PulseDot; the strip flips to "Live — <url>", and the engine posts "Deployed — … is live" into the session chat.
4. `art/visual` — design/creative: media frame (aspect per format), variant cycler "‹ 2 / 4 ›" (mono, centered under media), one caption line, "Change image" affordance on hover. Verbs: Use this · Request changes.
5. `art/sequence` — email/outbound: AUDIENCE block (who, in one sentence + the systems note "every send and reply is logged back to HubSpot") → SEQUENCE as numbered steps (mono number in the marker column, subject 12.5/600, timing sub "Day 4 · only if no reply", step-1 shows a body preview behind a 2px ink rule; merge fields render as mono CHIPS — green-50 pill, green-800 10px mono, e.g. “first name” — never raw braces) → foot "replies pause the sequence for that contact". Verbs: Request changes (ghost — files a request) · Approve & send → "✓ Added to the Work queue — sending <date time>". PIPELINE DOCTRINE: the console is NEVER a CRM — HubSpot is the system of record (a Knowledge source); prospecting exists only as sequence artifacts, queue jobs, and Performance views; deal detail deep-links to HubSpot; no contact management or deal editing, ever.
6. `art/plan` — job list rows (✓/pending ring, title+sub, state right) + outcome line. Verbs: Adjust · Approve plan.
7. `art/doc` — reports/digests rendered as a Markdown Kit file (header, sections, facts).
8. `art/rule` — a STANDING JOB's rule, composed from kit pieces: title + "standing job · cadence · agent" descriptor, "The rule" facts (cadence & delivery · client-facing or not · origin + "your approval covers the rule, never the output"), "Recent runs" md/table (mono date · result). Status strip: "Recurring · next run <date time> · runs without holding" (or "· each run holds for you"). Footer verbs "Change cadence" and "Pause rule" are NOT direct controls — both prefill a request in the composer, per the standing-job doctrine.
THE GENERATIVE CONTRACT (half templatised, half generative): agents never emit UI — they emit a TYPED PAYLOAD (body type + structured content: blocks, facts, current/proposed pairs, media refs, steps, run history) and the panel renders it through the kit. The frame, strip, footer and kit pieces are the templatised half; the composition and content are the generative half. Agent → default type: Strategist → plan/rule · Writer → article/post · Site → page · Pipeline → sequence · Analyst → doc. Anything unrecognised renders as art/doc — degraded gracefully, never broken, never free-form HTML.
Laws: a new deliverable format MUST map to one of these seven — extending the taxonomy is a design decision, never a dev improvisation. Bodies are composed only from existing kit pieces. The decision verbs name the real consequence (publish/deploy/send — never "release"). Publishing verbs are SPLIT BUTTONS: main segment approves with the default schedule; a chevron-up segment opens a schedule menu above (Publish now · Best slot — from memory, with a "your top-performing slot" subline · Pick a date & time). Every approval confirms "✓ Added to the Work queue — <schedule>" and the status strip flips to "In the Work queue · <destination> — <schedule>": the Work queue is where agents run, publish and edit, and every signal points there. Every approval/change writes memory. Panel = compact render; Expand ⤢ = THE universal viewer: the same panel grows in place to full width (bodies center at 680 measure), for EVERY artifact type, opened from anywhere — chat card, Work queue row, Home — always in place over the current screen, never as navigation. One component views all content; there is no separate full-screen sheet. Expanded measures per body: prose/doc bodies (article, page diff, sequence, rule) center at 680; art/post keeps the platform card at 552; art/visual caps media at 440 — full-bleed media at 1000px+ is a lie about the destination.
### Mock Kit — the pixel layer inside a body (codified 31 Jul; spec `Kit · Mock.dc.html`)
Inside `art/post`, `art/sequence`, `art/visual` and `art/plan` sits a MOCK: a still of the surface the work will land on. Five carry almost everything the engine makes — `mock/social-post` · `mock/direct-message` · `mock/crm` · `mock/landing-page` · `mock/email`. Each is drawn at its real measure with a documented anatomy (see the spec's Anatomy toggle for the labelled parts).
LAWS:
- **Anatomy, not skin.** Fidelity lives in proportion and hierarchy — 44px avatar, 1.91:1 media, 62ch email measure, 38px record row. We draw NO host platform's logo, wordmark or brand colour. A mock that needs someone else's logo to be recognisable is badly drawn.
- **The client is the only colour.** Mock chrome is grayscale; the colour inside comes from the client's identity in Design. Hivory green NEVER appears inside a mock — the single exception is a merge field (green-50 wash, green-800 text), because that marks where the engine writes. A landing-page mock in Hivory green is the most common mistake in this kit: it makes our brand look like their site.
- **Preview, never live.** Every affordance the real surface would offer is drawn at `--text-ghost` and does nothing. The only exceptions are the image slot (the client's own file goes in) and the one way out, below.
- **One way out.** A mock may carry exactly ONE live control, and it lives in the chrome, never in the content: **View website**, **Open in HubSpot**. It opens the real thing in a new tab and does nothing else — never approves, edits or changes state. Its label collapses to the glyph at compact width.
- **No invented numbers.** Follower counts, likes, open rates, deal values appear only from a connected account; otherwise omitted with one honest line ("Reactions appear once this is live"). Every real figure sets tabular-nums — since mono was retired that is what marks a machine fact.
- **Say where it came from.** Records carry a source and a sync age; personalised copy carries the evidence it was written from ("90 days of public activity — the aisle expansion, her two posts on packaging"); sequences carry their sending rules. Provenance is anatomy, not caption.
- **Truncate honestly.** Six rows then "6 of 118". Three lines then "…see more". A fade, never a hard stop.
- **Content reflows, layout scales.** A post, message, email or record table is a DOCUMENT: it reflows 408 → its own cap (post/DM/email 552, CRM 680) and its type size never changes; extra width becomes margin. A website is a LAYOUT: drawn once at 1000px and scaled as a true miniature (0.408 compact, 0.664 expanded), with our browser chrome at real size on top. Reflowing a landing page turns it into a different landing page; scaling an email turns it into unreadable type.
- **Shed, don't shrink.** Losing width drops columns and folds rails (the CRM's object rail becomes a count strip; Buyer and Stage fall away). Row heights, avatars and type sizes hold at every width. A mock that gets denser as it narrows is unreadable exactly when it matters.
- Screenshots are banned — a mock is DRAWN, so it stays sharp and stays editable.

RESOLVED 31 Jul — two boundaries the audit forced:
- **`mock/crm` depicts the DESTINATION, never our own review surface.** It is a still of HubSpot showing where records will land (object rail, provenance, six rows then truncate). The console's prospect-delivery table is a different object — Hivory's own Table for approving a batch, following Table's grammar (tabs, filters, our columns). Matching them would make our review surface pretend to be someone else's product. Consequence: the console table obeys Table's laws, so status is **a word, not a coloured pill** at row density (fixed 31 Jul).
- **`art/sequence` is not email-only.** Its payload carries a CHANNEL per step and the step renders the matching mock — `mock/email` for mail, `mock/direct-message` for social. One body, two mocks, per the generative contract. A mixed sequence shows each step in its own surface, which is the honest picture of what the prospect receives.

### Read vs review — one frame, two modes (codified 31 Jul)
The same artifact is reviewed in the console and shown in a proposal. One frame serves both; the mode swaps exactly three things and nothing else:
- **Header right** — review: ⎔ expand + ✕ close (the panel is a workspace). read: a leading glyph tile, a sub line naming the kind of work, and a tabular position counter (the artifact is one of a set being shown).
- **Status strip** — REVIEW ONLY. The strip reports live job state; a proposal artifact has no job yet, so there is no state to report and no strip to draw.
- **Footer** — review: the decision bar (owner meta left, verbs right). read: the provenance bar (origin left, the promise right — "Yours on signing"). Same 11px rhythm, no buttons.
NEVER changes: panel geometry and radius, body padding, every type size inside the body, the payload contract. A body is authored once against its typed payload and is MODE-BLIND — read mode simply mounts it with edit affordances off (no hover "+", no tracked changes, no image-slot drop, no cycler arrows, no composer). Nothing in a body may branch on mode; if a surface needs different content it needs a different PAYLOAD, not a different body.
RETYPE RULE: `art/page` summarises a CHANGE and needs a prior state to diff, which a proposal has not got. A page shown before any site exists is the page itself — so it is `art/visual` with a browser-chrome media frame. Never add a preview to `art/page` to make read mode work.

### Time & date standard (platform-wide)
All timestamps in the system face with tabular-nums (mono retired 27 Jul). Resolution follows distance — never more precision than the moment needs:
- happening now → `now` · today → time only `14:00` (24h, no am/pm, no seconds) · ANY other day, past or future → the DATE: `24 Jul` (day first, no leading zero), time stacked beneath when scheduling matters — in row columns the date sits on top (11px) with the clock muted below it (10px #B4B7B9); date and time are NEVER concatenated into one token · other years → `24 Jul 2025`. Weekday names NEVER appear in data columns — a weekday is not a date; in sentences a weekday may only prefix the full date ("Thu 24 Jul, 09:00").
- Recurring jobs: time column shows the next run (`Mon 08:00`); the status word carries the cadence (`recurring`).
- Relative words ("Today, 14:32" · "Yesterday" · "2 h ago") are allowed ONLY in sentence contexts — meta lines, colophons, memory provenance — never in data columns.
- Durations: `41s`, `6 min read`. One clock everywhere: same format in the queue, chat steps, memory, and colophons.
- DIRECTION: a timestamp never carries direction — the row's STATE does. Every dated row must sit under a state group or carry a state signal (scheduled/queued/running vs shipped/outcome), so `24 Jul` over `09:00` under a scheduled state reads forward and `21 Jul` beside an outcome reads back. A surface may NEVER mix future and past rows in one undifferentiated column — if a view ever needs both, they are separated by group (as the Work queue does) or the future rows take a sentence form ("publishes Thu 09:00") in the sub line. "Tomorrow"/"Yesterday" only in sentence contexts.
### Recurring work (standing jobs)
A recurring task is a STANDING JOB — a rule that emits ordinary jobs. The rule (cadence · next run · owning agent) lives in the jobs table once; each occurrence is a normal job with the normal gates. Laws:
- Approving the recurrence (in a plan or recommendation) approves the RULE, never the output: client-facing occurrences still hold for review every time (weekly LinkedIn post holds each week); non-client-facing ones (the Monday digest) run silently.
- In the queue, the standing job shows one row under IN PROGRESS: next run in the stacked date cell, "recurring" as the status word. Occurrences appear as their own rows only when live (held/running) or completed.
- Opening a standing job shows the rule as an artifact: cadence, next run, last runs with outcomes, and its origin (the accepted recommendation or plan).
- Changing or pausing a rule is a REQUEST through the chat — never a settings panel; the change writes memory like every decision.
- Active-state motion: "running" words breathe (1.6s opacity pulse, the chatThink curve) — the only animated text in the ledger.

### Performance (the proof layer)
DOCTRINE — Performance is a REPORT, not a dashboard. The Analyst writes it; the client reads it. The six fundamentals:

2. Adding cards: you don't add cards — you ASK. "Track refill orders here" is a request routed to the Analyst; the report changes as a job. No card builder, no drag-drop config, ever. REMOVING is direct (28 Jul): every report card — spine scorecards, hero chart, generated widgets — dismisses via the card-dismiss chip: a hover-revealed 20px white ✕ chip straddling the card's top-right corner (hairline ring + soft shadow, ink-400 glyph, #B91C1C on hover). 3. Dates: ONE global range for the whole page (quiet text presets top-right: 7 days · 30 days · Quarter · YTD; active = ink 650). Every number, chart and chain honors it. Per-card ranges are banned — that is how dashboards rot.
4. Export — the Get-as-PDF flow: the colophon carries ONE ghost verb ("Get as PDF") and nothing else — no compiled-from prose, no sync line (sync lives in Knowledge). ### Chart Kit (the graph library — spec + specimens in Kit · Chart.dc.html)
Four forms, one grammar; every generated graph is one of these, from a typed payload:
- `chart/line` — the default for anything over time: 2px green-600, round joins, 7% area fill, terminal dot; horizontal grid #EEF0EE only; 10px mono axis labels on the time standard; header = name + range + mono value + delta.
- `chart/bars` — discrete buckets ≤12 (else use line): 3px top radius, 60% band, history at 55% opacity, current bucket full green.
- `chart/hbar` — category comparison ≤6 rows, HTML tracks not SVG (label 110px · 8px rounded track · mono value right). This REPLACES every pie.
- `chart/spark` — scorecards only: no grid/axes, terminal dot, sits right of the mono value (64px in the spine).
- `scorecard/spine` — the fixed 4-card row: label + pinned delta on top, mono value + spark beneath; the ONLY place scorecards exist.
- `table/view` — the generated table: title + range header, ≤4 columns (label · numerics right mono · Δ last), ≤8 rows, provenance foot always ("Analytics · synced 12 min ago").
- `chart/compare` — comparison colors: current period green solid; previous period ink-300 DASHED 1.5px, no area, no terminal dot ("only the present gets ink"); legend mandatory at 2 series.
- `chart/tooltip` — EVERY chart element answers on hover, no exceptions: line points (chip + hairline guide + ring dot), bars (chip above the bar + full-green highlight), compare charts (ONE chip carrying both series: current green, previous gray beneath — never two chips), hbar rows (chip with share + mono value), sparkline scorecards (whole-card chip: start → current). Chip anatomy — ONE geometry everywhere: LEFT-aligned text (never centered), 12px side inset, content-sized width, 38px two-line box (10px gray context at baseline 15, 11px white mono value at baseline 30 — balanced ~8px vertical padding); values ALWAYS unit-labeled ("465 sessions", never a bare number); compare chips add a dot column (green + current white, gray + previous gray, 54px box). Chips NEVER clip: clamp inside the plot, flip below the point near the top edge; 120ms house ease; never persists, never stacks; table/hbar rows tint ink-2%.
- `chart/states` — loading = Skeleton shimmer in the plot area with the real header (never a spinner); empty = "Not enough data — connect <source>" + a Connect link; a chart never renders invented numbers.
Laws: one chart per card · series 1 = green-600 light / green-500 dark, 2–4 from the token ramp (teal · amber · ink), max 2 series in generated views · legend only at ≥2 series (one series = the header is the legend) · deltas green-700 up / #B91C1C down, inverted for cost metrics · mono tabular abbreviated values (18.2K · $41K · 1.8×) · empty = "Not enough data — connect <source>", never invented numbers. Banned forever: pies, donuts, gauges, radars, dual axes, 3D, vertical grid lines, y-axis lines, per-chart date pickers.

## Colour — token adoption & the drift rule (swept 31 Jul)
The portal ran on 1,805 raw hex values; 2,410 literals across 36 files are now `var()` tokens. Laws that came out of it:
- **Every colour comes from a token.** Three tokens were missing that this doctrine already NAMED in prose: `--chart-grid` (#EEF0EE, 43 uses, named in the Chart Kit spec), `--canvas-glow-green` (#DFF4E9) and `--canvas-glow-warm` (#EDEEE8) — the canvas gradient stops defined in Canvas & surfaces. If the doctrine names a colour, it is a token.
- **DRIFT ROUNDS TOWARD CONTRAST, NEVER TOWARD THE NEAREST VALUE.** #6E7072 (69 uses) sits between `--ink-600` at Δ25 and `--ink-500` at Δ16; collapsing it to the nearest dropped twelve runs of 9pt secondary text on the SIGNED CONTRACT from 4.9:1 to 3.3:1 — failing AA on the one deliverable that prints and cannot be zoomed. Same reasoning as the rhythm rungs: a stray resolves by MEANING, not by distance, and for colour meaning is legibility. Also collapsed: #7A7D80 (69 uses, an undocumented grey between ink-600 and ink-500) → ink-500 on screen surfaces.
- **Print rounds darker still — and print hierarchy is never colour.** Ink on paper has no backlight and no zoom, so EVERY word in a document clears 4.5:1: no exemption for labels, captions, running footers or page numbers. That rules out greying-out as a hierarchy device on paper — rank comes from size and weight, with tracking to quiet a label further. In the signed proposal all text sits at `--ink-600` or darker, and an 8pt/400 label at +0.04em reads as subordinate to an 11pt/600 value without spending contrast. (The first draft of this law exempted "labels whose words are already known"; measurement showed those nine runs at 2.63:1 and the exemption was deleted. Write the rule from the measurement, not the other way round.)
- **Small text has a floor, and it is a token (re-graded 31 Jul).** `--text-muted` was `--ink-500` at **3.34:1** and `--text-faint` was `--ink-400` at **2.63:1** — both fail AA as text, so every quiet run in the system failed with them. They now carry their own values: `--text-muted: #63676A` (5.71:1) and `--text-faint: #6F7376` (4.78:1, the lightest legal text in the system). The **ink ramp is unchanged** — `--ink-400`/`--ink-500` are still correct for borders, dots, meter tracks and marks, which have no contrast requirement. One edit to `colors.css` fixed 812 references across 38 surfaces without touching markup. Text ladder on white: ink-900 17.2 → ink-700 11.1 → ink-600 7.2 → muted 5.7 → faint 4.8.
- **Text contrast is measured against the DARKEST common background, never white** (31 Jul, after the third occurrence). `--text-faint` was first re-graded to 4.78:1 *on white* and still failed at 4.07:1 on `--ink-100` and 4.30:1 on the canvas — the product's real surfaces. Now `#676B6E`: 4.58 on `--ink-100`, 4.97 on `--ink-50`/`--surface-sunken`, 5.38 on white. `--text-muted` `#63676A` clears 4.86 on the worst case. Calibrate any new text token the same way, and record the worst-case surface beside it.
- **Prefer re-grading a token to documenting a trap.** This was found four separate times in one day by hand-authoring new markup, each time caught only by measurement. A rule that says "don't use this token for text" relies on everyone remembering; a token that cannot fail does not. #F4F5F4, #F1F2F0, #F7F8F7, #F1F2F1 all resolved to `--ink-50` — one step apart is a distinction nobody can see, and an invisible distinction is entropy (the same argument that killed 7-vs-8px and 160-vs-180ms).
- **Two exemptions, both principled.** (1) The CLIENT'S palette inside a mock stays literal — `--ink-*` in a client's landing page would make our brand look like their site (Mock Kit law). (2) SVG **presentation attributes cannot take `var()`** — `stroke="#fff"` must stay hex; 392 such values were deliberately skipped, along with 379 in logic classes that feed them. Colour destined for an SVG attribute is the one place a literal is correct.
- Files exploring another aesthetic (`Apple Explorations`, `Brand Identity*`, `Palette Directions`) are excluded from drift collapsing — their off-ladder colours are the point.

## Motion
SOFT-MOTION DOCTRINE (binding, 24 Jul; extended 31 Jul): soft everywhere. Every state change — hover, focus, selected, appear — eases gently on `--ease-out` at the DEFAULT `--duration-soft` 180ms; things settle, never snap. The only entrance is a 200ms fade on screen switch; no spin except the activity primitives (dual-hex spinner 1.15s, running/live pulse 1.6s). Spec + specimens: `Foundation · States & motion.dc.html`.
- **NOTHING LIFTS (31 Jul).** Hover and press are expressed as TINT, FILL, RING or BRIGHTNESS — never as displacement. No rise, no nudge, no scale: the cursor already says where you are, and a target that moves as you approach it is a worse target. `--hover-lift` is RETIRED (held at `0px` so the bundle still resolves; never reintroduce a lift). Movement is reserved for things that genuinely TRAVEL — the gliding selection pill, an arriving toast, a tooltip's `translateX(-50%)` centring — never for feedback.
- **Every duration and easing comes from a token.** There are no literal `ms` or `cubic-bezier` values anywhere in the system (120 declarations converted 31 Jul). 150 and 160ms were in use in sixteen places and were collapsed into `--duration-soft`: against 180 they are sub-perceptual, and a distinction nobody can see is entropy. Tokens: `--duration-fast` 120 press · `--duration-modal` 140 · `--duration-soft` 180 default · `--duration-screen` 200 · `--duration-slow` 240 · `--duration-gentle` 340 arrivals · `--duration-spinner` 1.15s · `--duration-pulse` 1.6s · `--ease-out` · `--ease-glide`.
- **motion-base** — three rules that cannot be written inline, so they live identically in every surface's one `<style>` block:
  1. **Focus ring** — 2px `--border-focus` outline at 2px offset, on `:focus-visible` ONLY, applied through `:where()` so it costs no specificity. A mouse click never draws a ring; a Tab always does.
  2. **Pressed** — a single system-wide `filter: brightness(0.94)` on `:active`. Chosen over opacity or transform because inline styles beat stylesheet rules: an opacity press would silently lose on every element that sets its own. Disabled controls opt out.
  3. **Reduced motion** — transitions and entrances collapse to 1ms, BUT motion that carries information (spinners, pulse dots, the queue's running word, skeleton shimmer) keeps looping at a calmed 2.4s. Removing it would delete the only signal that work is in flight. Mark it `data-motion="essential"`; when the animation comes from a CSS class instead, list the selector in that surface's reduced-motion block.
- **KNOWN GAP — keyboard operability.** 277 clickable `div`/`span` elements carry an onClick and NONE is keyboard-reachable: no tabindex, no role, so no focus ring however correct the rule. Deliberately NOT patched by adding tabindex in bulk — a focus stop that Enter and Space cannot activate is worse than none, because it promises an affordance the element does not have. Repair is per component: the right element (`button` where it acts, `a` where it navigates), the right role, and a key handler in the logic class.
